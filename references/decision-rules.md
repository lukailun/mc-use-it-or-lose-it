# 决策规则详解

本文件说明 `Mc-Use-It-or-Lose-It`（麦麦积分末班车）的核心判定逻辑，以及每条规则背后的依据。

---

## 规则一：以"先进先出"作为止损判定基础

**规则**
只要本期累计消耗积分 ≥ 本月将过期积分，本月过期风险即清零，无需精确指定消耗哪一笔积分。

**依据**
麦当劳积分在消耗时按先进先出原则扣减，优先扣掉最早获得、最早到期的那部分。因此"花掉快要过期的积分"这个诉求，等价于"本期消耗总额达到过期额度"。

**为什么重要**
忽略这条规则，就会陷入"想精确花掉 9.9 分"的错误目标。而现实中最小消耗颗粒是整次抽奖（如 24 分）或整件商品（如 50 分），不可能精确匹配。认清这一点，问题才从"凑单"变成"找最小覆盖"。

---

## 规则二：抽奖方案的次数计算

**规则**

```
需要抽奖次数 = ⌈本月将过期积分 ÷ 单次消耗积分⌉
总消耗       = 次数 × 单次消耗
可行条件     = 总消耗 ≤ 可用积分
```

**示例**
本月将过期 9.9 分，单次消耗 24 分 → ⌈9.9 / 24⌉ = 1 次，消耗 24 分即可覆盖。

**边界**
将过期积分为 0 时直接判定"无需抽奖"，不参与推荐。

---

## 规则三：单次消耗取自 `drawDecision`，而非活动配置

**规则**
单次抽奖消耗取 `query-lottery-info.data.drawDecision.nextConsumption.points`。

**依据**
`drawPoint` 是活动配置的标称值，而 `drawDecision` 是服务端针对当前用户算出的**本次实际消耗**。在"先消耗次数再消耗积分"的混合规则下，`nextConsumption.type` 可能为 `CHANCES`（本次不扣积分），两者并不等价。

同时，抽奖资格只以 `drawDecision.resourceEligible` 为准。即使 `availableTimes` 为 0 或 null，只要 `nextConsumption.type == "POINTS"`，就仍可用积分抽奖——**不得**依据 `availableTimes` 或 `drawTypeText` 自行推断。

---

## 规则四：商品时效以时间窗口为主判据

**规则**

```
可兑换 ⟺ status == 2
         且 (downTime 为空 或 now ≤ downTime)
         且 (upTime  为空 或 now ≥ upTime)
```

**依据**
`mall-points-products` 的 `status` 字段存在**滞后**：`downTime` 已过期的商品仍会返回 `status: 2`（上架）。

真实样例验证：16 个返回商品中有 7 个实际已过兑换截止时间（如商品 `spuId=15866`，`downTime` 为 `2026-06-24`，但 `status` 仍为 2）。若直接照搬原始列表，用户会看到大量无法兑换的商品。

因此以 `upTime`/`downTime` 与服务器当前时间的比较作为**主判据**，`status` 仅作辅助；被剔除的商品数量需明确告知用户。

**时间基准**
统一使用 `now-time-info` 返回的服务器时间，而非本地时间，避免时区或设备时钟偏差。

---

## 规则五：兑换方案取"最小覆盖"

**规则**
在**当前在售**且**可负担**的商品中，选 `point ≥ 本月将过期积分` 的最小积分商品。

**依据**
目标是止损过期积分，而非获取最大价值。选刚好覆盖过期额度的商品，可让"单位积分换取的止损效果"最高，同时把可用积分的消耗降到最低。

**缺口处理**
若无商品可覆盖且积分不足，输出与最低门槛商品之间的缺口，建议先点餐攒分或等待新一期活动——**不推荐**用多件低价商品强行凑数，因为那属于引导额外消费。

---

## 规则六：两个方案间的取舍

**规则**
在可行的抽奖方案与可行的兑换方案中，取**消耗积分更小**者；消耗相同时取剩余积分更多者。

**依据**
止损的本质是"用最小代价消除过期风险"。抽奖有随机性（未中奖也消耗积分），兑换有确定性收益，因此当两者消耗接近时，工具会在输出中同时呈现两个候选，把选择权交给用户，而非替其决定。

---

## 规则七：区分"将过期"与"已过期"

| 字段 | 含义 | 可操作性 |
|---|---|---|
| `currentMouthExpirePoint` | 本月将过期 | ✅ 本工具的作用对象 |
| `nextMouthExpirePoint` | 下月将过期 | ⚠️ 提前预警 |
| `expiredPoint` / `lastMouthExpirePoint` | 已过期 | ❌ 既成损失，不可找回 |

**依据**
三者语义完全不同。把已过期积分计入"待处理额度"会让用户误以为还有救，产生错误预期。因此输出中必须分开呈现，并明确说明已过期部分无法挽回。

---

## 附：判定优先级

```
1. 本月将过期积分 == 0  →  输出"无需操作"，结束
2. 抽奖可用（drawDecision.resourceEligible 且 nextConsumption.type == POINTS）
   且 总消耗 ≤ 可用积分  →  纳入候选
3. 在售商品中 point ≥ 过期积分 且 point ≤ 可用积分  →  取最小者纳入候选
4. 候选存在  →  取消耗更小者推荐，并同时列出另一候选
5. 候选为空  →  输出缺口金额，建议攒分 / 等待新活动
```

全程只读计算，任何真实消耗动作都需用户明确确认后单独执行。
