# 麦麦积分末班车（mc-use-it-or-lose-it）

麦当劳积分有固定有效期，到期未用即自动失效扣除、不累计到次月，且不可找回。本 Skill 的唯一目标：**在积分过期前，用最小的消耗把「本月将过期积分」花掉**。

不推荐"最划算的套餐"，不诱导多消费，只回答一个问题——**这笔快过期的积分，怎么花最不亏**。

## 触发场景

- 积分余额查询："我有多少积分""积分还有多少"
- 过期风险查询："我积分什么时候过期""这个月有多少积分要过期"
- 活动与商品查询："积分抽奖有什么奖品""积分能兑换什么"
- 止损执行："帮我把快过期的积分花掉""我要抽奖""我要兑换这个"

## 核心概念

麦当劳[《会员服务协议》](https://www.mcdonalds.com.cn/page/member-service-agreement)规定的积分有效期：当月（第 n 月）内获得的积分的有效期截止至获得积分当月起的第 n+12 月的最后一天的 24 点。每个月月末都有一批积分清零，到期未用即自动失效扣除、不累计到次月。
因此判定标准很直接——**只要本期累计消耗 ≥ 本月将过期积分，本月过期风险即清零**，无需精确指定消耗哪一笔。

这一条是整个 Skill 的推理基础。缺少它就会陷入"想精确消耗 9.9 分"的死胡同，而实际最小消耗颗粒是整次抽奖或整件商品。

## 工作流

### 第 1 步：确认账户

若尚未配置 `mcd-mcp` 连接器，先引导用户配置（见 `mcp-config.example.json`），并说明需要先到 [open.mcd.cn/mcp](https://open.mcd.cn/mcp) 申请 MCP Token。

### 第 2 步：并行拉取四份数据

以下四个只读工具**必须并行调用**，避免串行等待：

| 工具 | 用途 |
|---|---|
| `now-time-info` | 返回当前的完整时间信息，以便于 LLM 知道当前的时间和日期 |
| `query-my-account` | 查询用户积分账户信息，包括可用积分、累计积分、冻结积分、即将过期积分等 |
| `query-lottery-info` | 查询当前积分抽奖活动的基本信息，包括活动状态、奖品列表、抽奖消耗规则和用户可用资源 |
| `mall-points-products` | 查询麦麦商城内可使用积分兑换或现金购买的商品 |

### 第 3 步：运行积分计算

把四份返回拼成一份 JSON，交给计算脚本：

```bash
python3 scripts/points_planner.py --input <输入文件>
```

输入结构见 `examples/sample-input.json`。脚本输出：
- 抽奖方案可行性、需要抽几次、共消耗多少分
- 当前**在售**商品清单（已按积分升序、已剔除过期商品）
- 最省的"一次兑换覆盖过期积分"选项
- 明确的推荐动作与风险提示

需要机器可读结果时加 `--format json`。

### 第 4 步：呈现结果

按脚本输出组织回复，固定包含四块：**账户快照 → 抽奖方案 → 兑换方案 → 建议**。表格优先，金额和积分保留原始精度。

### 第 5 步：用户确认后执行消耗

用户明确选择「抽奖」或「兑换」后，才进入写操作。**两条路径的确认要求不同，不可混用**：

**抽奖路径**
1. 重新调用 `query-lottery-info` 取实时 `drawDecision`，**不得复用旧数据**
2. 向用户展示 `drawDecision.nextConsumption` 的具体消耗文案
3. 用户明确确认后调用 `draw-lottery`
4. 抽奖频次受限，同一用户短时间重复调用会返回"操作太频繁"且不扣分——不要重试轰炸
5. 抽奖资格与消耗**只以 `drawDecision.resourceEligible` / `nextConsumption` 为准**。即使 `availableTimes` 为 0 或 null，只要 `nextConsumption.type == "POINTS"` 就仍可用积分抽奖，**严禁**自行推断不可抽

**兑换路径**
1. 从 `mall-points-products` 选定 `spuId`
2. 调用 `mall-product-detail` 取 SKU 列表与 `shopId`（必须为 `2`），让用户选具体 SKU
3. 虚拟商品（`spuCategory=1`）直接下单；实物商品（`spuCategory=2`）需先取收货地址 `addressId`
4. 调用 `mall-create-order` 完成交易
5. 多件商品**必须分别下单且串行排队**，前一笔响应成功后再发下一笔
6. **禁止**跳过 `mall-create-order` 直接输出"兑换成功"

若商品属于生日派对 / 主题派对 / 麦麦体验营 / 品鉴会 / 读书会 / 积分兑换活动等需选门店场次的类型，改用 `party-order-create`，不要走 `mall-create-order`。

## 参数正确性红线

- `query-my-account` 返回的积分是**字符串**（如 `"1572.5"`），参与比较前必须转数值，不要按字符串排序
- `mall-points-products` 的 `status` 字段**存在滞后**：`downTime` 已过仍可能返回 `2`（上架）。**时效判断必须以 `upTime`/`downTime` 与当前时间比较为准**，`status` 仅作辅助
- 单次抽奖消耗取 `drawDecision.nextConsumption.points`，不要用活动配置的 `drawPoint` 直接替代（混合规则下两者可能不同）

## 输出规范

- 积分数值保留一位小数，整数不补 `.0`
- 兑换商品必须同时给出：名称、所需积分、兑换截止时间、`spuId`
- 本月无过期积分时，明确告知"无需操作"，**不要**为了促成消耗而制造焦虑
- 累计已过期积分属于**既成损失**，说明清楚不可找回，避免用户误以为本次操作能找回

## 安全边界

- 本 Skill 只读操作可自由执行；**抽奖与兑换是真实消耗行为，必须先取得用户明确确认**
- "看看吧""如果可以就抽"不构成确认
- 不做批量抽奖、不做连续抽奖、不做试抽
- 不存储、不记录用户的 Token 与账户凭证
